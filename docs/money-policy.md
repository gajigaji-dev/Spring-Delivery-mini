# 금액 처리 정책

[← README](../README.md)

원 단위 금액의 타입, 결제 건별 수수료·정산액 계산 규칙. 기간별 정산 집계는 [정산 기준](settlement-policy.md) 참고

| 구분 | 타입 | 이유 |
|---|---|---|
| 원 단위 금액 (가격·총액·결제액·수수료·정산액) | `long` / `bigint` | 원화는 소수점이 없는 정수 금액. `int`(최대 약 21억 원)는 대량 주문 총액에서 넘칠 수 있어 `long` 사용 |
| 수량 | `int` / `integer` | 금액이 아니므로 그대로 유지 |
| 수수료율 | `BigDecimal` / `numeric(5,4)` | 소수점 비율. `double`은 0.05 같은 값을 정확히 표현하지 못해 오차가 생김 |

- **계산**: 소수점이 생기는 계산(금액 × 수수료율)만 `BigDecimal`로 하고, 결과는 원 단위 `long`으로 저장 (`entity.PaymentFee`)
- **반올림**: 수수료를 **원 단위 HALF_UP**(0.5원 이상 올림)으로 **한 번만** 반올림
  - 예: 18,009원 × 5% = 900.45원 → 900원 / 18,010원 × 5% = 900.5원 → 901원
- **정산액**: 따로 반올림하지 않고 `결제액 - 수수료`로 계산 → 수수료 + 정산액이 항상 결제액과 같음 (반올림 오차로 1원이 사라지거나 생기지 않음)
- **공통 수수료율**: `application.yml`의 `payment.fee.rate` (기본 `"0.05"`, 실제 계약 요율이 아닌 임시 통일 값). 0 이상 1 이하, 소수점 4자리까지만 허용하고 벗어나면 기동 실패
  - double을 거치지 않도록 문자열로 지정
- **매장별 수수료율** (V10, #32): `stores.fee_rate` — 관리자만 설정·해제 (`PUT`/`DELETE /api/admin/stores/{id}/fee-rate`)
  - 범위·자릿수 규칙은 공통 수수료율과 같음 (0 이상 1 이하, 소수점 4자리)
  - 수수료율은 플랫폼 내부 정보 → 공개 매장 조회(`StoreResponse`)에는 포함하지 않음. OWNER 전용 조회 API도 없음 (점주는 정산 조회의 결제별 `feeRate`로 실제 적용된 수수료율을 확인)
- **적용 수수료율 결정** (`Store.effectiveFeeRate`): **결제 시점**에 매장 수수료율 → 없으면(`NULL`) 공통 수수료율
  - `0.0000`(수수료 0%)과 `NULL`(공통 수수료율 사용)은 다른 의미
  - 결정된 수수료율을 결제마다 `payments.fee_rate`에 스냅샷으로 저장 → 매장·공통 수수료율을 바꿔도 이미 저장된 결제의 수수료·정산액은 바뀌지 않음
  - 기준은 결제 시각 — 결제 후 배달완료 전에 수수료율이 바뀌어도 그 결제는 결제 시점 수수료율로 정산되고, 환불 차감도 결제에 저장된 금액 그대로
  - 정산(`settlements` 등)은 결제별 저장 금액을 더하기만 하므로 수수료율 변경으로 이미 만들어진 정산(확정·지급 포함)이 바뀌지 않음
  - 수수료율 변경과 결제가 동시에 일어나면 결제 트랜잭션이 읽은 시점에 커밋된 값이 적용됨 (적용된 값은 `fee_rate`에 남음)
- **총액 계산**: 항목 금액은 `Math.multiplyExact`, 합산은 `Math.addExact`로 계산해 `long` 범위를 넘으면 400 응답 (잘못된 값이 저장되지 않도록, `Order.addItem`)
  - 요청 본문의 가격이 `long`, 수량이 `int` 범위를 넘으면 JSON 변환 단계에서 400
- **수수료 도입 전 결제**: V3 마이그레이션에서 수수료 0, 정산액 = 결제액으로 채움
- 수수료·정산액은 사장님/플랫폼 내부 정보라서 CUSTOMER가 받는 결제 응답(`PaymentResponse`)에는 포함하지 않음 → 사장님용 정산 조회 API(`GET /api/stores/{id}/settlements`)의 별도 DTO(`StoreSettlementResponse`, `SettlementItemResponse`)로만 제공
- 참고: `long` 금액을 JSON 숫자로 내보내므로, 2^53(약 9천조 원)을 넘는 금액은 JavaScript 클라이언트에서 정밀도가 손실될 수 있음 (현재 요구 범위에서는 해당 없음)
